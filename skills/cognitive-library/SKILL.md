# 认知库（cognitive-library）

个人认知库是一组**本地 Markdown 文件**：文章和卡片放进去，按分类索引，彼此可以有关系。
它不是聊天记录的备份，也不是记忆系统——它的产品是**能重新读、能复述、能发给别人的文字**。

## 两种条目，自己判断

入库前先判断：这份材料能不能撑起一条完整的思路？

| 类型 | 判断标准 | 大致篇幅 |
|---|---|---|
| `article` | 有前因后果、有推进过程，值得读者跟着走一遍 | 能展开就展开 |
| `card` | 只是一个判断、一条经验、一个结论，三两句说得清 | 几百字以内 |

篇幅不是标准，完整度才是。不要为了显得有结构而把一段判断凑成文章，也不要硬把一条完整论证压成卡片。
同一份材料通常产出一条；如果里面确实还有别的独立判断，可以另外存，但不要为了数量去拆。

## 什么材料该整理

- 用户粘来的一段话、一份 Markdown/PDF 的内容
- 一次聊天（当前会话，或用户指定的若干轮）
- 一个网页链接、公众号或知乎文章（正文提取失败时，请用户直接粘贴正文）
- 用户明确说"把刚才那个整理一下""存进认知库"

## 默认是整理，不是改写

拿到材料先问一句：原文有没有自己的骨架？

- **有**（分点、分节、有收束）——沿用它。顺序不改，层级不并，标题不换。你的工作是去重、补连接、修断裂。
- **没有**（一段流水、层次混乱、前后重复）——才重组，并且动手前先说明打算怎么改。

判据很硬：**整理完能逐句对回原文。** 如果某一节在原文里找不到对应，那多半是你在改写，不是整理。

原文已经写得清楚时，改得越少越好。把一篇逻辑通顺的文章重排成"论文腔"，是典型的失败——读者会立刻感到陌生，而且会丢掉原文的推进感。

## 整理成什么

**文章**：先看原文的推进方式。

- 原文是"可能性 → 失败原因 → 案例 → 结论"这种递进，就保留这个递进，别改成"结论先行"。
- 原文是"先给判断，再展开论证"，就保留判断在前。
- 原文确实没有结构，才用结论先行、逐层展开。

**不要为了"显得有结构"重排小标题。** 小标题用原文的功能性说法（"为什么这些路径都失效"），不要生造概念（"约束的形状""失效点""软肋"）。

判断标准只有一条：**半年后重读，能顺着它想起当时的推理过程。**

可以自然带上的东西（有用就写，不硬凑）：
- 这条判断成立的条件、反例
- 还没想清楚、需要验证的问题
- 关键论据的出处（来自哪一轮对话、哪一段原文）

**你自己的补充要和原文分开。** 想加反驳、补案例、提疑问，放到正文之外的「附」里并注明是编者补充，不要混进原文的论证里——混进去，读者就分不清哪句是原作者的意思。

**卡片**：一句判断 + 两三条支撑，写完就停。

## 别写出 AI 味

- 小标题是天然的翻译腔重灾区：不要"约束的形状""失效点""三重逻辑"这类抽象命名，用大白话。
- 不要为了对称硬凑三段式排比，不要每节都以一句总起句开头。
- 少用"不是 A，而是 B""与其说……不如说……"这类句式；一句话能说完就说完。
- 不要动不动"本质上是""归根结底"——那是判断，不是装饰。
- 保留原句的用词习惯。作者写"多子多福"，你别改成"生育激励不足"。

## 分类

- 分类是**受控**的，不是自由标签。默认五个：政治、经济、科技、心理、生活（以实际库里的为准，先 `cognitive_category list` 看一眼）。
- 现有分类都不合适时，**先问用户**要不要新建，让用户起名字，再用 `cognitive_category add`。不要自己发明。
- 一句话讲不清归类时，用 `待归类`，别硬塞。
- 标签（tags）是自由的，用来标具体对象：`#RAG`、`#组织设计`、`#开源`。

## 关系，不合并

两条内容互相呼应、互相反驳、互相补充时，用 `cognitive_relate` 连起来并写一句说明。
**不要合并、不要改写已有条目。** 关系是附加信息，正文保持原样。

## 重新分类

用户要求调整分类体系时：
1. 用 `cognitive_category rename <旧> <新>`（会自动迁移条目并重建索引）
2. 建新分类后再逐条改归属，然后 `cognitive_reindex`
不要重写文章正文——重新分类只改归属和索引。

## 落盘

优先用工具（保证 frontmatter、index.md、graph.md 一致）：

- `cognitive_save` —— 写一条（title / body / type / category / tags / summary / source）
- `cognitive_list` / `cognitive_search` —— 先查有没有相近内容，避免重复入库
- `cognitive_relate` —— 建立关系
- `cognitive_category` —— list / add / rename
- `cognitive_reindex` —— 重建 `index.md` 与 `graph.md`

没有这些工具时，直接按下面的结构写文件：

```
<库根目录>/
  index.md              按分类索引（生成物）
  graph.md              关系图（生成物）
  cards/<日期>-<标题>.md
  articles/<日期>-<标题>.md
  .cogni.json           分类表
  relations.json        关系数据
```

条目文件的 frontmatter：

```yaml
---
id: "2026-10-24-示例"
type: "card"            # card | article
title: "一句话标题"
category: "科技"
tags: ["RAG", "上下文"]
summary: "一句话结论"
created: "2026-10-24"
updated: "2026-10-24"
source: {"kind":"chat","ref":"本次会话"}
---
```

## 入库前的自检

1. 先 `cognitive_search` 查有没有讲过同一件事——有就补一条关系或更新，而不是再造一条重复的。
2. 分类存在吗？不存在就先问用户。
3. 这是文章还是卡片？看内容能不能独立成篇，不看字数。
4. 写完给用户一句回执：存成什么、归到哪、文件在哪。
